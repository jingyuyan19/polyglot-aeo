# Polyglot AEO — Plugin UI Localization Guide

This document explains how Polyglot AEO's own UI is translated, and how to
add a new language.

> **Note**: this is for the **plugin's interface** (buttons, labels, helper
> text). It is independent of your Framer project's content locales — the
> tools the plugin generates (schema, llms.txt, meta) work for *any*
> language regardless of which UI language you pick.

---

## Architecture at a glance

| Concern             | Where                                              |
| ------------------- | -------------------------------------------------- |
| Locale codes & meta | `src/i18n/types.ts`                                |
| Source strings (EN) | `src/i18n/locales/en.ts` (the source of truth)     |
| Other locale files  | `src/i18n/locales/<code>.ts` (must mirror EN)      |
| Runtime store       | `src/i18n/index.ts` (`initI18n`, `useI18n`, `t`)   |
| Persistence key     | `polyglot-aeo:ui-locale-preference` (plugin data)  |
| Auto-detect input   | `navigator.languages` → `navigator.language`       |

We use:

- **Zero runtime dependencies** — no `i18next`, no `react-intl`. The plugin
  bundle stays small.
- **TypeScript template literal types** — every legal `t()` key is derived
  from `en.ts` at compile time. If you add a key to `en.ts`, every other
  locale file becomes a TypeScript error until you add the same key.
- **`useSyncExternalStore`** — switching language re-renders only the
  components that subscribe via `useI18n()`, not the whole tree.

---

## How the active locale is decided

On boot (`src/main.tsx → bootstrap()`):

1. Detect from `navigator.languages` and `navigator.language` (the browser
   inside Framer's Plugin SDK reflects the user's OS / browser language).
2. Load the persisted preference from plugin data.
3. If the user picked `auto`, the active locale = the detected one.
   Otherwise the active locale = the picked one.

The user can change their preference in **Settings → Plugin language**.
Picks persist per Framer project.

## How to use translations in code

```tsx
import { useI18n } from "../i18n"

function MyView() {
  const { t } = useI18n()
  return (
    <>
      <h1>{t("dashboard.subtitle")}</h1>
      <p>{t("schema.localesPartial", { n: 2, total: 5 })}</p>
    </>
  )
}
```

Outside React (e.g. inside a `framer.notify` call deep in an async handler),
use the imperative form — it reads the current snapshot:

```ts
import { t } from "./i18n"

framer.notify(t("schema.installSuccess", { n: 4 }), { variant: "success" })
```

### Interpolation

Placeholders use the `{name}` syntax:

```ts
// en.ts
"localesActive": "{n} active",

// usage
t("dashboard.localesActive", { n: 5 })  // → "5 active"
```

### Pluralization

We deliberately keep this simple: pass `n` and use separate keys for
singular vs. plural where it matters. Most languages we ship don't need
the full ICU plural ladder.

```ts
"installButton": "Install {n} block",
"installButtonPlural": "Install {n} blocks",
```

```tsx
const label =
  n === 1
    ? t("schema.installButton", { n: 1 })
    : t("schema.installButtonPlural", { n })
```

For languages without grammatical plurals (Chinese, Japanese, Korean), the
two keys can be identical — both forms read naturally.

## How to add a new language

Steps, in order. Each step is a small, mechanical change.

### 1. Add the locale code to `src/i18n/types.ts`

```ts
export type SupportedLocale = "en" | "zh-CN" | "ja" | "ko"
//                                                    ^^^^

export const LOCALE_METADATA: Record<SupportedLocale, LocaleMetadata> = {
  // …existing entries…
  ko: {
    nativeName: "한국어",
    englishName: "Korean",
    matchPrefixes: ["ko"],
  },
}
```

`matchPrefixes` controls the auto-detect: any `navigator.language` value
that equals one of these prefixes (or starts with `<prefix>-…`) resolves
to this locale. For most languages a single BCP-47 primary tag is enough.

### 2. Create `src/i18n/locales/ko.ts`

Copy `src/i18n/locales/zh-CN.ts` as a starting point — it's the most
similar in shape (same `Translations` type) — and translate every value.
Keep the keys identical.

```ts
import type { Translations } from "./en"

export const ko: Translations = {
  common: {
    back: "뒤로",
    save: "저장",
    // …
  },
  // …
}
```

If you forget a key, TypeScript will tell you.

### 3. Register it in `src/i18n/index.ts`

```ts
import { ko } from "./locales/ko"

const TRANSLATIONS: Record<SupportedLocale, Translations> = {
  en,
  "zh-CN": zhCN,
  ja,
  ko,
}
```

That's it. The language picker in Settings reads `LOCALE_METADATA`
automatically, so the new language shows up there with no further wiring.

### 4. Verify

```sh
npm run typecheck   # surfaces missing keys
npm run dev          # change OS language → confirm auto-detect works
```

## Translation principles

These are guidelines I use when adding `zh-CN` and `ja`. Translators for
new languages should adapt these for their own audience.

### 1. Keep technical terms in their canonical form

Don't try to translate `JSON-LD`, `schema`, `inLanguage`, `OG`,
`Twitter Card`, `llms.txt`, `BCP-47`, `AEO`, `SEO`. Designers searching
for help on these will Google the English term anyway.

### 2. Keep brand and product names untranslated

`Polyglot AEO`, `Framer`, `ChatGPT`, `Perplexity`, `Claude`, `Anthropic`,
`OpenAI`, `Google AI Overviews` — never translate.

### 3. Local punctuation

Use the punctuation conventions of the target language:

- Chinese: `，。：；！？` (full-width)
- Japanese: `、。`
- French: `« » ` ; `:` (with non-breaking space before `: ! ? ;`)

### 4. Avoid literal translation

If the English source is marketing copy ("Get cited by ChatGPT in every
language"), do not translate word-for-word. Rewrite to sound natural in
the target language. The intent matters, not the syntax.

### 5. Match the tone of comparable native plugins / SaaS in your market

Chinese designer SaaS tends toward: concise, technical, no buzzwords.
Japanese tends toward `です・ます` (polite professional) form.
German tends toward `Sie` (formal you), even in product UI.

When in doubt, look at how Notion, Linear, or Figma localize their UI for
your target locale.

## Adding a new key (when extending the plugin)

1. Add the key to `src/i18n/locales/en.ts`. This is the source of truth.
2. TypeScript will immediately flag every other locale file as missing
   the key. Add a translation to each one.
3. Use it via `t("path.to.key")`. The key is autocompleted by your IDE
   from the type derived in step 1.

If you don't speak the other languages, leave the value identical to the
English one as a placeholder and open an issue tagged
`i18n: needs translation` listing the keys.

## What is *not* translated

Some things are intentionally English-only across all UI locales:

| Thing                                | Why                                       |
| ------------------------------------ | ----------------------------------------- |
| BCP-47 codes (`en-US`, `zh-CN`, …)   | Industry standard; designers expect these |
| Schema property names (`inLanguage`) | They're literal JSON-LD field names       |
| API key prefixes (`sk-ant-…`)        | Vendor-specific identifiers               |
| `Polyglot AEO` brand                 | Brand consistency                         |

Helper text *around* these may reference them in the local language —
that's fine. The literal codes themselves stay English.
